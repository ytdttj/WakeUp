## WakeGuard：缓解 KB5121003 电源回归导致的息屏

### 背景
联想笔记本安装 Windows 11 2026-08 安全更新 KB5121003（25H2 → 26200.9168）后触发已知回归：
系统误报 AC 适配器断开 1~5 秒，Modern Standby 机器随即息屏并滑入连接待机。
微软/联想均未官方承认，9 月更新未修复，该补丁已随 9 月累积更新固化、无法单独卸载。

### 本机实测诊断结论（后续排查可直接复用）
- 睡眠架构：**Modern Standby (S0ix)**，S3 不可用，休眠未启用
- 电源计划：睡眠 / 休眠 / 关闭显示 的超时，**AC 与 DC 均为 0（从不）**
- 唤醒定时器：AC 启用、**DC 禁用** → 决定了「睡了再唤醒」方案不可行
- 事件日志实锤：Kernel-Power **105** 成对出现（间隔 1 秒 = AC 掉电/恢复）；
  Kernel-Power **506 / 507 = Modern Standby 进入 / 退出**，两天各 17 次，这就是「息屏」的真身
- 无 Power-Troubleshooter 唤醒记录 → 从未真正进入传统睡眠
- 屏保：`ScreenSaveActive=1` 且 `SCRNSAVE.EXE` 为空 → 纯黑屏，**不受电源请求约束**

### 方案与实现
- 用户态无法否决已进入的睡眠转换（Vista 起取消 veto），故采用**预防式**，而非「休眠后唤醒」
- `PowerCreateRequest` + `PowerSetRequest(DisplayRequired / SystemRequired)` 持续持有
- **AC 去抖 sticky = 60 秒**：最近 60 秒内出现过 AC 在线即判定为物理接电，完全吸收 1~5 秒误报
- 尊重手动操作：锁屏 / 合盖 / 菜单放行时自动释放请求
- 托盘用 pystray + PIL；隐藏消息窗口（纯 ctypes）接收 WM_POWERBROADCAST 与 WTS 会话通知
- 单实例用命名互斥量 `Local\WakeGuard_Singleton_Mutex`，句柄须存全局防止被 GC

### C# 版踩到的三个 Win32 坑（务必记住）
1. `WNDCLASSEXW` 结构体**必须**标 `[StructLayout(LayoutKind.Sequential, CharSet = CharSet.Unicode)]`，
   否则 string 按 ANSI 封送，类名注册成乱码，`CreateWindowExW` 报 **1407 ERROR_CANNOT_FIND_WND_CLASS**
2. `CreateIconFromResourceEx` 要的是 **RT_ICON 资源体**（BITMAPINFOHEADER 开头），
   不是 .ico 文件（带 ICONDIR 头），传错会失败且 GetLastError=0
3. 别用 GDI（CreateDIBSection/RoundRect/Polygon）画托盘图标，实测进程直接崩；
   改为在代码里构造 32bpp 像素数组 + CreateIconFromResourceEx，稳定且无 GDI 依赖

### 追加：C/Win32 版（最终采用，用户要求最小占用）
- `src/wakeguard.c` → `bin/WakeGuardC.exe`，**34.5 KB**（C# 版 10,676 KB，约 1/309）
- 实测：私有内存 **2.54 MB** / 工作集 12.91 MB / 6 线程
  （C# 版 11.1 MB 私有、8 线程；Python 版约 40-60 MB）
- 编译命令（Strawberry Perl 附带的 MinGW GCC）：
  `gcc -O2 -s -mwindows -fexec-charset=UTF-8 -finput-charset=UTF-8 -o WakeGuardC.exe wakeguard.c -luser32 -lshell32 -ladvapi32 -lgdi32`
- 设计：单线程 Win32 消息循环 + WM_TIMER(500ms)，无 CRT 之外的任何依赖；
  电源/会话/WTS 等可能不在旧导入库里的 API 一律 GetProcAddress 动态解析

### MinGW 编译坑
1. `POWER_REQUEST_TYPE` 与 `REASON_CONTEXT` **已由 winnt.h / minwinbase.h 定义**，不要重复声明
2. `windows.h` 不会自动包含 `shellapi.h`；`NOTIFYICONDATAW`、`NIM_*`、`NIF_*`、
   `Shell_NotifyIconW`、`ShellExecuteW`、`CommandLineToArgvW` 都要显式 `#include <shellapi.h>`
3. `WTS_SESSION_LOCK/UNLOCK`、`ERROR_ALREADY_EXISTS` 需自行 #ifndef 兜底
4. 中文菜单用窄字符串 UTF-8 字面量 + `MultiByteToWideChar(CP_UTF8)` 转换，
   配合 `-fexec-charset=UTF-8` 可正常工作（不要直接写 L"中文"，编译器字符集不可靠）

### 追加：自启动问题（联想电脑管家不弹窗）
- 现象：用户点托盘「开机自启动」无效，且联想电脑管家没有弹出自启权限确认窗
- 已加入的能力（C 版）：
  1. 写入 Run 键后**立即弹窗**报告结果 + Win32 错误码（5=被拒绝）
  2. 新增 **「开机自启动（启动文件夹）」**：在 `shell:startup` 放 .lnk，完全绕开注册表 Run 键
     （IShellLinkW + IPersistFile，链接 -lole32 -luuid；体积 34.5 → 86 KB）
  3. 新增「复制自启动诊断信息」到剪贴板
  4. 命令行：`--autostart on|off|folder|folderoff`
- 排查要点：先确认注册表里是否**已存在旧的 WakeGuard 值**（Python 版遗留），
  若已存在则菜单显示勾选、点击实为「取消」→ 删除操作，管家不会弹「添加」确认窗
- **C 陷阱**：`Log("...", SetAutoStartFolder(1), AutoStartFolderOn())` —— 函数参数求值顺序未定义，
  GCC 从右向左，导致读到的是操作**前**的状态。必须先赋值再传参
- **剪贴板编码坑**：`SetClipboardData(CF_TEXT, ...)` 传 UTF-8 字节会被 Windows 按本地代码页(GBK)解释而乱码；
  必须用 **CF_UNICODETEXT** + MultiByteToWideChar 转换
- 诊断项改为文字化（已启用/未启用、已创建/不存在）+ 记录 g_lastRegError，并弹窗直接显示，不依赖剪贴板
- 已确认启动文件夹快捷方式真实存在（783 字节），开机自启走这条路已生效
